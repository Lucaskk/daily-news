# 每日全球與科技 AI 新聞產製規則

本檔是 `wiki/daily/` 每日新聞報告、來源筆記與網頁簡報的固定規則。每日自動化開始選題前必須先讀取本檔。

### 可回退的研究模式（2026-09-15）

- 每次產製先用 `python3 scripts/news_workflow.py status` 確認模式；pipeline也會輸出目前模式。legacy沿用原本搜尋／rg流程；python使用同程式的lookup與fetch輔助，仍需AI判讀。預設legacy，不因新功能已存在就自行切換。
- 使用者可直接執行 `python3 scripts/news_workflow.py mode legacy` 切回，或 `mode python` 啟用。設定不改日報、公開頁、配送成功紀錄或防護；詳細操作見 [新舊流程切換](workflow-switch.md)。
- 9/14事故稽核與修正限制見 [9/14未產製事故](incident-2026-09-14.md)。維持同一對話每天08:00，不新增補跑；新使用者指令與停止要求仍優先。

### LINE 指令與節省 token 分工（2026-09-14）

- 本機 LINE 背景程式使用 `~/.codex/automations/ai/tech_source_store.py` 與 `tech-sources.csv`，避免 macOS 限制背景程式讀取 Documents。工作目錄的 `wiki/daily/config/tech-sources.csv` 連到同一份實體 CSV；保留連結，編輯內容即可。CSV 程式以解析後的實體路徑做原子寫入，不覆蓋連結。

- LINE 私訊 `查看網址` 可列出本機 CSV 的全部來源（包含停用），顯示網址、加入時間、網站名稱、類別、啟用狀態、加入來源與備註。使用既有每 15 分鐘 watchdog 回覆；長清單會分成多則訊息，不截斷欄位。電腦須開機並連網，內容以實際本機 CSV 為準。

- 科技產品候選來源改由本機 [config/tech-sources.csv](config/tech-sources.csv) 管理；每日 `scripts/news_workflow.py status` 讀取 `enabled=true` 的列。CSV 欄位為 `url`、`added_at`（Asia/Taipei）、`website`、`category`、`enabled`、`origin`、`note`。舊有來源的實際加入時間不明，因此 `added_at` 留空，新增來源會自動填入。本機可直接新增或刪除整列；暫時停用可把 `enabled` 改成 `false`。也可執行 `python3 scripts/tech_source_store.py add https://example.com --website 名稱 --category 類別`。網址是候選發現來源，個別新聞仍須核對發布時間、原始來源與最近 14 天日報去重。
- LINE 私訊指令格式為 `加入網址 https://example.com`，也接受 `增加網址` 與 `新增網址`，限既有授權使用者的一對一訊息。Bot 先將事件寫入新聞庫的 `wiki/daily/source-requests/YYYY-MM-DD/`；本機每 15 分鐘由既有 watchdog 讀取，去重後寫入 CSV 並回覆結果。電腦關機或 Bot 尚未部署時不會立即入檔；收到「已加入」回覆後才代表本機 CSV 已更新。網站名稱預設為網域，可再於本機編輯。

- 使用者明確要求補發歷史日期時，可於核對原截點、完成日期網頁並驗證 Pages 後，使用唯一私人 watchdog 的 `--backfill-date YYYY-MM-DD`。只接受過去7天；獨立補發紀錄，不修改今天入口、正常配送成功日期或舊失敗 checkpoint。一般每日排程不得自行使用此入口。若原日期已有不確定的配送請求，須先核對，不繞過去重。

- 「重新產出」目前定義為先自動診斷：既有 LINE Bot 接收授權的一對一指令，原有 watchdog 回報產製／公開頁／配送狀態；不自行啟動模型、不重設當日研究截點、不繞過配送去重。
- Python 處理索引、固定檢查、渲染、發布、配送與已知錯誤分類；Codex 處理來源查證、事件語意去重、選題與摘要。完整分工及限制見 [Python 與 Codex 分工](python-ai-division.md)。

## 一、全球新聞採 24 小時，科技產品採 14 天

1. 每日執行時先記錄 Asia/Taipei 研究截點，並建立兩個獨立時間窗：全球／世界新聞為截點前 24 小時；科技／AI 產品為截點前 14 天（336 小時）。
2. 全球 Top 10 的事件、官方發布或重大新進展必須落在 24 小時窗內；不得因數量不足而放寬。
3. 科技產品項目可從 14 天窗內挑選，但只限首次推出、正式發布、預購／上市、公開測試、重大功能更新、重大可用性／權限變更、停用或具體產品路線更新。純折扣、導購、舊開箱、重刊、評論、傳聞或沒有產品狀態變更的產業文章不得補位。
4. 自 2026-10-03 起，科技／AI 新聞每日最少 1 則、最多 10 則。搜尋截點前 14 天內、最近 14 天日報未曾收錄的產品事件，依重要性選取最多 10 則；不用湊滿 10 則。先掃描本機 CSV 啟用來源，再針對官方 newsroom、release notes、產品發布與公開測試補查，涵蓋硬體、消費軟體、開發工具及 AI。若仍找不到任何合格項目，明確記錄未達最低數量，繼續研究並回報原因，不可刊登虛構、逾期或重複新聞。
5. 不以文章頁面的「更新時間」單獨判定。舊事件即使被重新整理、改標題、重發或仍在首頁熱門，也不得當成新事件或新產品。
6. 全球續報可以沿用較早背景，但重大新進展本身必須落在 24 小時窗內；科技新聞只選 14 天窗內、最近 14 天日報未曾收錄的獨立事件。
7. 滾動新聞頁、live blog、官方 release notes 與 changelog 必須定位到視窗內的確切貼文、版本日期或更新項目；不能只引用整個持續更新頁面。
8. 若來源沒有精確時間，至少需能確認發布日期與事件時間落在對應視窗內；無法合理確認時排除。
9. 來源筆記必須同時記錄全球 24 小時窗與科技產品 14 天窗的 Asia/Taipei／UTC 起訖，並為每則入選項目保留事件／發布時間依據。

## 二、跨日去重是強制規則

1. 只比對產製日前 14 個日期的每日整理報告（D−14 至 D−1），不比對 14 天以前的日報、完整歷史表或歷史來源筆記；當日產製中的報告不當作歷史重複。
2. 去重判斷以「事件或產品變更」為單位，不以標題文字、語言、媒體或網址是否不同為準。同一事件換標題、換來源或換摘要仍算重複。
3. 科技／AI 新聞必須是最近 14 天日報未曾收錄的獨立產品事件，不再以同事件續報補位。既有公司或產品的新獨立變更仍可列為候選，但不得只是已收錄事件的後續說明或不同媒體報導。全球 Top 10 仍允許可驗證的重大新進展，須標示續報。
4. 新聞數量不足時，應改選其他重要新事件；不得用舊聞、背景資料、同一官方更新頁或「仍值得關注」的理由補位。
5. 同一個滾動更新頁、官方 release notes 或 live blog 可以再次作為來源，但只有頁面出現明確的新日期、新功能、新命令、新裁決或新事件時，才能形成新的新聞項目。
6. 選題前執行 `python3 scripts/build_product_news_ledger.py --cutoff 研究截點ISO時間`，只讀上述 14 天日報，產生 `wiki/daily/product-news-recent-14d.md`；舊完整歷史表僅保留存檔。
7. 候選以公司、產品、變更動作與比對鍵做窄化搜尋，使用 `python3 scripts/news_workflow.py lookup --cutoff 研究截點ISO時間 --pattern 組合查詢詞`。工具只搜尋 14 天日報；標題、語言、媒體或網址不同但事件相同，仍算重複。
8. 查無命中時可核對同一 14 天範圍的產品表；不得把更早資料混入判斷。
9. 產品表每列代表一次產品變更，保留公司、產品、更新、發布時間、收錄日期、狀態、來源與比對鍵。

## 三、什麼才算重大續報

本節適用全球新聞的續報。科技新聞以未曾收錄的獨立事件為限。符合下列任一情況，才可重新收錄既有全球主線：

- 草案變成正式簽署、生效、投票結果、法院裁決或政策執行。
- 產品由預告進入正式發布、公開測試、全面供應、停用或重大權限變更。
- 戰爭、災害或公共安全事件出現新的地點、攻擊、傷亡、停火破裂或可驗證的戰略變化。
- 官方公布足以改變原先判讀的新數字、證據、調查結論或矛盾說法。
- 事件從政治表態進入法律、外交、制裁、交易或制度程序的新階段。

下列情況不算重大續報：

- 另一家媒體重述同一件事。
- 標題、引言或政治人物措辭略有不同，但事件狀態未改變。
- 只增加評論、背景、預測或市場猜測。
- 同一數字、同一產品功能或同一公告被再次引用。
- 只因事件仍熱門、仍重要或需要補足篇數而重列。

## 四、續報的寫法

1. 標題必須以 `續報｜` 開頭。
2. 內文必須指出上一次收錄日期與內容，例如：「2026-06-13 已收錄 final text 說法；今日新進展是提出具體簽署時程，而伊朗公開否認該日期。」
3. 必須清楚分開「已知舊背景」與「今日新增事實」，不能把背景重新包裝成新消息。
4. 若新增內容不足以單獨構成新聞，應放在背景、來源筆記或後續追蹤，不得占用當日新聞名額。
5. 重要性相近時，優先選擇全新的事件，而不是續報。

## 五、每日來源筆記必須留下時間與去重紀錄

每份 `source-notes-YYYY-MM-DD.md` 至少包含：

- Asia/Taipei 研究截點、全球新聞 24 小時窗，以及科技產品 14 天窗的明確起訖時間。
- 每則入選新聞的事件時間、首次可靠發布時間或官方更新時間依據。
- 去重搜尋範圍。
- 當日保留的續報、前次收錄日期與重大新進展。
- 因重複或只有小幅更新而排除的候選事件。
- 滾動更新頁或 release notes 所使用的確切更新日期／段落。
- 矛盾報導與尚未確認之處，不得以其中一方說法覆蓋另一方。
- 每個科技候選的窄化查詢詞、命中與排除結果，以及實際比對的 14 天日報日期範圍。

## 六、科技產品來源與查證

### 逐站查閱紀錄（2026-10-06 起）

- 每日先執行 `python3 scripts/news_workflow.py scan`，保留每個啟用來源的取得時間、成功／失敗、內容雜湊與私人原始內容路徑。`status` 只列出設定，不代表已查閱；`scan` 成功也不代表完成選題。
- 下列第 2 條的批次搜尋須搭配逐站確認：每站檢視最新文章、RSS 或逐站搜尋，來源筆記列出實際文章網址、可核實發布日期、候選及採用／排除理由。找不到候選須記錄實際檢查範圍。第一輪廣泛搜尋不可限縮至已選定的單一產品。
- 空內容、舊頁或失敗必須依第 4 條補查；未完成補查標示待查，不得宣稱全站已查或只有目前則數合格。私人快取路徑不得加入 Git。
- 評測與導購若提及新品線索，先回查其官方首次發布日期再判斷。仍維持 14 天時間窗、最近 14 天日報去重與每日 1–10 則。

1. 每次科技候選搜尋以 `scripts/news_workflow.py status` 輸出的 CSV 啟用來源為準，檢查最新產品、AI、裝置、軟體、運輸與重大功能消息。初始清單包含 [Engadget](https://www.engadget.com/)、[The Verge](https://www.theverge.com/)、[TechCrunch](https://techcrunch.com/)、[WIRED](https://www.wired.com/)、[Ars Technica](https://arstechnica.com/)、[Cool3c](https://www.cool3c.com/)、[Yahoo奇摩科技](https://tw.news.yahoo.com/tech-news/)、[TechOrange 科技報橘](https://techorange.com/) 與 [數位時代](https://www.bnext.com.tw/)；本機 CSV 新增或停用的來源會反映在清單中。
2. 上述媒體構成每日候選來源池，用於發現候選、交叉核對與補充國際／台灣市場脈絡。先以批次搜尋或聚合頁掃描多個來源；第一輪未取得足夠合格候選時，按第 4 條再做一輪定向補查，不必逐站無限深挖。只有出現合格候選線索時才開啟文章與官方來源。當日來源筆記需列出兩輪實際搜尋範圍、候選數、去重與排除原因。
3. 對每個候選涉及的公司或專案，優先回查官方 newsroom、產品頁、新聞稿、release notes、changelog、支援文件或監管文件。規格、價格、上市日、支援市場、效能與公司聲明，原則上以可定位日期的官方資料為準；官方資料不存在時，需由至少一個可靠媒體來源明確標示不確定性。
4. 若來源因付費牆、robots、登入、地區限制或技術錯誤無法讀取，來源筆記需記錄失敗，並改用該站 RSS、搜尋結果中的原始文章、其他可靠媒體或官方來源補查；不可把「無法讀取」當成「沒有新聞」。
5. 商品快報、Shopping guide、特價、業配、評論、觀點、傳聞與舊產品導購不得單獨構成產品新聞；只有其中指出可核實的新品、正式發布、預購／上市、公開測試、重大功能或可用性變更時才列為候選。
6. 對每個科技產品候選至少比對公司、產品名稱／型號、變更動作、事件日期與來源網址；同一產品換媒體或換語言仍算同一事件，繼續沿用 14 天窗與最近 14 天日報去重規則。

## 七、標題與展開內容

- 標題使用繁體中文完整句，清楚交代主體、動作與結果；公司、產品與模型正式名稱可保留英文。
- 不使用只有關鍵字的片語、抽象口號或中英混雜且無法獨立理解的標題。
- 每則全球新聞與科技／AI 新聞都必須在標題正下方顯示首次可靠發佈時間及可讀出處。已知精確時間統一換算為 `Asia/Taipei`，格式為 `發佈時間｜YYYY-MM-DD HH:mm:ss（Asia/Taipei）`，HTML 的 `<time datetime="...">` 保留對應 UTC ISO 8601 值。來源只有日期時保留 `YYYY-MM-DD` 與「官方發布日期／事件日」說明，`datetime` 也只填日期，不虛構 00:00:00 或時區轉換。
- 每個展開項目必須包含核心事件，並至少補充背景、影響、關鍵數字或不確定性中的一項。
- 除首頁來源索引外，每個新聞展開內容在來源區塊前，目標至少 80 個非空白字元；不得以重複句或無資訊文字湊字數。

## 八、簡報與來源

- 自 2026-09-08 起採用使用者提供的手機閱讀參考：單欄文章、清楚的產品／主題圖、標題、發佈時間、出處、短摘要及 2–3 點關鍵事實。深色為預設並提供淺色切換；正文不可放進多層卡片，亦不以大封面擋住第一則產品。
- 所有新聞、數字、科技摘要與後續追蹤項目都必須可點選展開。每篇下方設「詢問後續問題」、「完整報告」與「分享」；分享使用該日期頁面加上 `story` 查詢參數與新聞錨點的雙重定位網址，任一定位資訊仍存在時都要直接開啟指定新聞。支援裝置原生分享，無法使用時改為複製連結。完整報告使用原頁 `<details>` 展開／收合，不可跳往 Markdown、另一個 HTML 或外站，也不可只展開來源連結。
- 完整報告保留背景與影響、事件／發佈依據、收錄或續報紀錄、相關實體、不確定性及完整來源；這是本站完整新聞筆記，不代表轉載媒體原文。
- 若當日有合格科技產品，第一個閱讀區優先放 1–3 則最高價值產品，再依序列其餘產品和全球新聞；每則在頁面只出現一次，不再重複「封面焦點」與「完整科技清單」。舊規則的歷史日報無合格產品時直接顯示全球新聞；新版產製至少需要 1 則合格科技新聞，也不得把 14 天窗產品誤標為今日發布。
- 每個展開項目的最下方必須放自己的來源區塊，顯示可讀標籤與完整原始網址。
- 不得把新聞來源集中放在投影片浮動頁尾；底部區域保留給導覽控制。
- 發布前確認每個新聞／追蹤展開項目皆有自己的非空白來源群組；ChatGPT 對話框的純文字預覽不算新聞卡片。
- 仍保留科技／全球／研究備註分類、逐篇上一則／下一則、新聞目錄與左右方向鍵導覽。手機可自然上下捲動，展開後不可因固定高度、頁尾或水平換頁而裁掉內容。
- 主題分組可以用於目錄或分節標題，但不可為分組而重複一篇新聞、刪減內容或強迫無關新聞同頁。

## 十、可靠性、執行環境與發布順序

每日排程必須依下列順序執行，避免非必要的本機預覽或工具依賴阻擋手機發布與 LINE 通知：

1. 先按凍結研究截點重建最近 14 天產品表，使用 lookup 在相同 14 天日報範圍內查候選；不搜尋或重建完整歷史索引。
2. 使用 Python 標準函式庫完成必要的結構驗證；不要安裝或載入 workspace dependencies。
3. 若既有生成器或 JavaScript 語法檢查確實需要 Node，先使用 `command -v node`；若找不到，固定改用 `/Applications/ChatGPT.app/Contents/Resources/cua_node/bin/node`。不得因 PATH 沒有 `node` 而呼叫 dependency loader、建立套件環境或中止發布。
4. 發布到 GitHub `main`，確認當日 dated deck 與 `latest-slides.html` 在 GitHub Pages 均回應 HTTP 200。
5. 發布驗證成功後，執行 `/Users/lucas/.codex/automations/ai/line_watchdog.py`。這是自動化唯一的 LINE 發送入口；不得再依專案 `.env` 判斷或直接呼叫其他 LINE sender，以免設定分岔、重複發送或日誌誤報。
6. LINE 程式結束碼為 0 且輸出包含 `Sent LINE message` 或 `already sent` 時，才可把 LINE 狀態記為成功；任何其他結果都要在 `wiki/log.md` 與 automation memory 記錄實際錯誤。
7. localhost 預覽是最後的 best-effort 步驟。Port、背景 server、瀏覽器渲染或 Playwright 問題不得阻擋 GitHub 發布、LINE 發送或最終摘要。

若當日檔案已產生但排程即將中斷，優先完成「發布 → LINE → 狀態紀錄」，不要把剩餘時間花在可選的本機 server 或視覺檢查。
